## Technical Findings

### 1. VM Process Lifecycle

**Observation:** The BasicVibeCodeApp host process (PID 70958) terminated, but the VM at 192.168.64.2 continues to respond to network requests.

**Implication:** This is **expected behavior** for Virtualization.framework VMs. Once started, VMs run as independent processes managed by the hypervisor, not tied to the parent application's lifecycle.

### 2. MAC Address Configuration Issue

**Problem:** Configured MAC `52:54:00:12:34:90` does not match actual MAC `6a:1:60:6d:ef:38`.

**Root Cause:** The `VZNATNetworkDeviceAttachment` API does not accept a custom MAC address parameter. The MAC is auto-generated by the framework.

**Impact:**
- DHCP leases will not be stable across VM restarts
- VM IP may change between boots
- Agent 21 cannot reliably correlate VMs to configured MAC addresses

**Recommendation:** Use `VZBridgedNetworkDeviceAttachment` with a custom `VZMACAddress` for stable MAC addresses, or implement VM-to-IP discovery via serial console parsing.

### 3. Console Output Inaccessibility

**Problem:** Console logs expected at `/tmp/vibecode-console-*.log` were not found.

**Possible Causes:**
- macOS App Sandbox restrictions preventing /tmp writes
- Console logs written to sandboxed container temp directory
- BaseVMManager not creating console file handle correctly
- VM process terminated before console timer started

**Recommendation:** Update BaseVMManager to log console path on initialization for debugging.
