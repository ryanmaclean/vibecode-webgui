================================================================================
KEY FINDINGS
================================================================================

Finding 1: NETWORKING FAILURE IS IDENTICAL IN BOTH HYPERVISORS
   - Both vfkit and Virtualization.framework fail to detect eth0
   - Root cause is NOT the hypervisor but the initramfs configuration
   - Missing virtio-net kernel driver in initramfs affects both equally

Finding 2: VFKIT SHOWS BETTER PORT FORWARDING CAPABILITY
   - vfkit accepts TCP connections to port 3000
   - Virtualization.framework refuses connections (port blocked)
   - vfkit's NAT implementation appears more complete
   - However, HTTP traffic doesn't reach the guest (buffering issue?)

Finding 3: OPENVSCODE IS RESILIENT TO MISSING NETWORKING
   - Application starts successfully without network interface
   - Binds to 127.0.0.1:3000 (localhost only)
   - Can serve local requests but cannot reach external clients
   - Error handling gracefully skips MAC address detection

Finding 4: INITRAMFS-ONLY BOOT HAS FUNDAMENTAL LIMITATIONS
   - Cannot dynamically load kernel modules
   - All drivers must be built into kernel or packed in initramfs
   - Current setup lacks virtio-net driver entirely
   - Modern deployments typically use disk-based root filesystems

RECOMMENDED SOLUTIONS
================================================================================

Solution 1: REBUILD INITRAMFS WITH VIRTIO-NET DRIVER (RECOMMENDED)
   Priority: HIGH
   Effort: MODERATE (1-2 hours)
   Expected Result: eth0 interface detection + networking

   Steps:
   1. Extract initramfs: gunzip -c initramfs.cpio.gz | cpio -id
   2. Get virtio_net.ko from Alpine Linux kernel modules
   3. Add to: lib/modules/6.6.63/kernel/drivers/net/virtio_net.ko
   4. Update init script to: insmod lib/modules/.../virtio_net.ko
   5. Rebuild: find . | cpio -H newc -o | gzip > initramfs-fixed.cpio.gz

Solution 2: USE DISK-BASED FILESYSTEM
   Priority: MEDIUM
   Effort: HIGH (build new image)
   Expected Result: Full filesystem with dynamic module loading

   Advantages:
   - Can install packages dynamically
   - Can load kernel modules at runtime
   - Better for production deployments
   - More flexible configuration

Solution 3: SWITCH TO LIMA

================================================================================
CONCLUSION
================================================================================

The networking issue is NOT a difference between vfkit and Virtualization.framework.
Both fail identically because the initramfs lacks the virtio-net kernel driver.

However, vfkit demonstrates BETTER port forwarding capability:
- Accepts connections (NAT works)
- Hypervisor-level routing works
- Issue appears to be at guest level (response not flushed/returned)

RECOMMENDATION:
1. Rebuild initramfs with virtio-net driver support
2. Use vfkit for production (shows better networking promise)
3. Or switch to Lima for immediate working solution
4. Long-term: migrate to disk-based filesystem approach

The fix is straightforward - just need to add the kernel module to initramfs.
Both hypervisors are fundamentally capable; the issue is purely an initramfs
configuration problem affecting both equally.
